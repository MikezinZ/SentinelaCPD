01 / Plataforma

Da mensagem ao histórico.

A arquitetura atual usa um serviço de ingestão entre o broker e o banco de dados.

Fluxo atual de dados

  1. 01ESP32Sensores e RMS
  2. 02EMQXMensagens MQTT
  3. 03IngestorValidação em Python
  4. 04MySQLLeituras e incidentes
  5. 05API + interfacesApp e dashboard

Serviços executáveis com Docker Compose em um servidor da rede local. Uma implantação remota depende de hospedagem, acesso de rede e configuração de segurança.

Mensageria e ingestão

Identidade por dispositivo

O ID fixo do ESP32 compõe o tópico MQTT. O ingestor valida os campos e grava as leituras, a versão do firmware e os eventos recebidos.

  • sentinela/<id>/telemetria
  • sentinela/<id>/evento
  • sentinela/<id>/ota e /cmd/ota (atualização de firmware)
  • Usuário, senha e ACL: cada placa só publica e lê os tópicos do próprio ID.
  • Compatibilidade com o tópico legado da N1.
Dados e operação

Histórico, API e alertas

MySQL mantém dispositivos, leituras, eventos, incidentes e alertas. A API FastAPI fornece acesso às interfaces; um serviço de notificações integra os alertas ao Telegram.

O backend recebe eventos de falta e retorno de fonte. Sua geração no equipamento depende do circuito de detecção configurado.

Wi-Fi conectado não significa dados entregues

A conexão à rede local, o acesso ao broker e a gravação no banco são etapas distintas. O firmware publica em QoS 0; o retorno de publicação não confirma persistência no MySQL. MQTT sem TLS é destinado à bancada; o transporte TLS opcional exige configuração do broker, certificados e credenciais.

02 / Dispositivos

Coleta autônoma na borda.

O firmware executa no ESP32 sem exigir um computador conectado durante a operação.

Firmware

Coleta separada da comunicação

Uma tarefa FreeRTOS produz amostras a cada 5 segundos. Outra parte do programa atende Wi-Fi, portal e MQTT. As tentativas de conexão não são pré-condição para coletar sensores.

A fila mantém somente a última amostra. Ainda não há histórico persistente das medições offline.

Configuração local

Troca de Wi-Fi pelo celular

Com o firmware iniciado, segurar BOOT por pelo menos 5 segundos reabre o portal protegido. A rede anterior permanece salva até a nova conectar e obter IP.

Função implementada; exige validação na placa. Use BOOT após iniciar, sem pressionar EN junto.

Como configurar a rede

  1. Abra o portal pelo BOOT ou ligue o dispositivo sem rede cadastrada.
  2. Conecte à rede SentinelaCPD-… com a senha própria do dispositivo.
  3. Acesse http://192.168.4.1 e informe o Wi-Fi de 2,4 GHz com senha pessoal.
  4. Aguarde o teste de conexão. Após salvar, o portal fecha em 15 segundos.

A janela dura até 10 minutos. Após cerca de 60 segundos sem Wi-Fi, o firmware tenta abrir o portal de recuperação. Durante a configuração, a coleta continua e o envio MQTT fica suspenso. O cadastro atual não implementa login corporativo ou portal de convidados.

Processamento do sinal de corrente

O cálculo RMS usa a variação do sinal em relação à média de uma janela de 200 ms e aplica um fator de calibração. Abaixo de 18 unidades ADC de RMS, a leitura é zerada para reduzir o piso de ruído. Isso é processamento de sinal, sem modelo de IA embarcado nesta versão. Corrente zero não comprova falta de tensão, e a medição não fornece diretamente potência ou consumo em kWh.

Energia • a validar

Continuidade e eventos de fonte

O código prepara a leitura de tensão e os eventos POWER_LOSS e POWER_RESTORED. São necessários um sinal condicionado de presença de fonte e um circuito adequado de medição da bateria.

No exemplo, os pinos estão em −1 e os dados saem como indisponíveis. O percentual, quando habilitado, é uma estimativa linear, não autonomia garantida. A fila de até quatro eventos é volátil.

OTA • pela dashboard

Atualização remota de firmware

O administrador envia o .bin no dashboard; a API confere placa, versão e SHA-256 e manda o comando por MQTT. O ESP32 baixa o arquivo com token de uso único, confere o hash, grava no slot livre e reinicia. Se a nova versão não confirmar o funcionamento em 90 s, o bootloader volta para a anterior (rollback).

Recusa arquivo inválido, de outra placa ou versão igual/anterior, e só atualiza fora da bateria. Download por HTTP na rede local (integridade pelo SHA-256); HTTPS é o próximo passo. O OTA por manifesto assinado com RSA continua disponível como alternativa.

Reconexão MQTT com espera progressiva e watchdog foram implementados. Abertura do portal e ciclo OTA são coordenados para evitar execução simultânea. Esses mecanismos não substituem testes integrados de falha.

03 / Aplicativo

Dados para acompanhar e decidir.

Aplicativo móvel em React Native/Expo e dashboard web em React, com contrato de API compartilhado.

Acompanhamento

Dispositivos e histórico

Consulta das métricas, atualização das leituras e histórico com agregações. Estados de dado recente, antigo ou indisponível ajudam a interpretar o que está sendo exibido.

Operação

Alertas e incidentes

Alertas por limites configurados, reconhecimento com nota e consulta de incidentes de energia. Limites são regras do servidor; não são enviados ao ESP32 nesta versão.

Administração

Usuários, dispositivos e firmware

No dashboard, o administrador cadastra usuários, muda perfis, desativa e redefine senhas; vincula, renomeia e desativa dispositivos; envia e instala novas versões de firmware acompanhando cada etapa.

Acesso

Login e permissões

Perfis de administrador, operador e visualizador, com controle de ações na API. Esse login é independente da senha do portal Wi-Fi do dispositivo.

Demonstração e dados do equipamento são modos diferentes

Os exemplos de configuração do app e do dashboard ativam dados simulados. Para mostrar telemetria real, é necessário desativar os mocks, apontar para uma API acessível e conferir a chegada de leituras novas. Este GitPage apresenta o projeto; ele não hospeda a API nem executa o aplicativo.

04 / Tecnologias

Tecnologias utilizadas.

O que usamos em cada camada do projeto e a função de cada tecnologia. Versões indicadas quando fazem diferença.

1. Aplicativo mobile

CaracterísticaO que usamos
Linguagem de programaçãoTypeScript: tipagem dos contratos da API compartilhada com o dashboard web.
Framework / SDKReact Native 0.88 com Expo SDK 58 e Expo Router: um código para iOS e Android, com navegação por arquivos.
IDE / ambiente de desenvolvimentoVS Code e Expo Go no celular para testar sem compilar o app.
Bibliotecas / plugins principaisexpo-secure-store (guarda o token de login no armazenamento seguro do aparelho), react-native-gifted-charts (gráfico do histórico), NativeWind (estilos) e lucide-react-native (ícones). Requisições com fetch nativo.
Integração com o projetoAcessa somente a API REST /api/v2 com token JWT. Não fala com o broker nem com o ESP32: telemetria, alertas, histórico e limites chegam pela API.

2. Sistema embarcado / firmware

CaracterísticaO que usamos
Placa e microcontroladorESP32 (ESP32-WROOM-32, dual-core Xtensa LX6, 4 MB de flash) em placa com suporte para bateria 18650. Sensores: DHT22 (temperatura e umidade), ZMCT103C (corrente AC) e PC817 (presença da fonte; circuito previsto, ainda não instalado na placa).
Linguagem de programaçãoC++ (Arduino), com as regras críticas em cabeçalhos testados no PC.
IDE e framework / SDKArduino IDE 2 com o núcleo arduino-esp32 3.3 (baseado no ESP-IDF 5.5). Perfil alternativo em ESP-IDF puro em firmware-idf/.
Sistema operacional / RTOSFreeRTOS: sim (o do ESP-IDF). A coleta dos sensores roda em uma tarefa própria, e uma fila guarda a última amostra, para que Wi-Fi e MQTT não atrasem a medição.
Bibliotecas e recursos principaisWiFi e WebServer (portal para configurar a rede pelo celular), Preferences/NVS (rede salva), PubSubClient 2.8 (MQTT), DHT 1.4.6, HTTPClient + mbedTLS (download e SHA-256 do firmware), esp_ota_ops (OTA em dois slots com rollback) e watchdog.

3. Plataforma IoT / backend / nuvem

CaracterísticaO que usamos
Local de hospedagemNotebook local na rede do laboratório. Futuro: VM em nuvem com o mesmo Docker Compose e HTTPS.
Linguagem e framework do backendPython 3.12: FastAPI + Uvicorn na API, paho-mqtt no ingestor (recebe do broker, grava e gera alertas) e no envio de comandos de OTA.
Serviços e produtos utilizadosEMQX 5.8 (broker), MySQL 8.0 (banco), Telegram Bot API (avisos de queda de energia, temperatura e dispositivo offline). Nenhum serviço pago de nuvem.
Implantação e orquestraçãoDocker Compose com 5 serviços (emqx, mysql, ingestor, api, notifier) e volumes persistentes. Sobe com docker compose up -d --build.
Persistência e administraçãoMySQL com leituras, eventos, incidentes, alertas, limites, usuários, versões de firmware e histórico de OTA. Dashboard web em React + Vite: monitoramento, alertas, usuários, dispositivos e atualização de firmware. Login com JWT e perfis (visualizador, operador, administrador). API REST documentada no Swagger.

4. Comunicação e integração

CaracterísticaO que usamos
Protocolos utilizadosMQTT 3.1.1 (telemetria, eventos e comandos de OTA), HTTP/REST (apps e download do firmware) e Wi-Fi 2,4 GHz.
Broker / gateway / servidorEMQX 5.8.0 em contêiner. Tópicos por dispositivo: sentinela/<id>/telemetria, /evento, /ota e /cmd/ota.
Formato dos dadosJSON nas mensagens MQTT e na API; arquivo binário .bin no download do firmware.
Segurança de comunicaçãoBroker com usuário e senha e ACL por tópico (cada placa só usa os tópicos do próprio ID; só a plataforma envia comandos). API com JWT de 15 min e senhas com PBKDF2. Firmware com SHA-256 e token de download de uso único. TLS (MQTTS e HTTPS) é o próximo passo, antes de sair da rede local.
Fluxo entre camadasESP32 → EMQX → ingestor → MySQL → API → app e dashboard. No sentido contrário, dashboard → API → EMQX → ESP32 para a atualização de firmware.

5. Case / invólucro do produto

CaracterísticaO que usamos
Software de modelagem 3DCadQuery (modelagem paramétrica em Python) para gerar as peças; Tinkercad para visualizar e conferir.
Formato dos arquivosSTL (uma peça por arquivo, para o fatiador) e STEP (montagem CAD completa).
Processo de fabricaçãoImpressão 3D FDM na Anycubic Kobra 3 V2.
Material e parâmetros relevantesPLA, camada de 0,20 mm. Oito arquivos STL; cerca de 10 h 30 min e 257 g de filamento no total (base 7 h 53 min).
Integração mecânicaCâmara separada para o DHT22, longe do calor do ESP32; passagem própria para o condutor no ZMCT103C; porta da bateria por fora, com 2 parafusos M3; furo para o LED de status; aberturas de ventilação; placa fixada em pilares.
